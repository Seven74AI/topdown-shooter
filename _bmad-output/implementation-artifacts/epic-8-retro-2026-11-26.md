## 2. What went well

- **Numeric rules first worked for timing code (Epic 6 A3).** The ACs set numbers: freezes per 30 s, KB/s, percentage of reversed hits, percentage of shots over the cap. Reviewers reproduced them exactly ("12 measurement rows reproduce exactly", log :80). 8.8, 8.9 and 8.10 each needed **only 1 re-review round**, against Epic 6's 2.6 passes per build [V].
- **Reviews blocked exploits before they shipped.** 8.1's review found free +50 % heals (H1, H2) and boss-HP cheese from held seats (H3). 8.2+8.3's review found loot farming via leave and rejoin (H2) and a reused id that inherited a bank (H1). 8.4–8.6's review found one loot bag paying more than once (H1) [V].
- **The switch to PRs with a CI gate worked fast.** Timeline: PR #7 (triggers) was green at 13:51. PR #10 cut CI from 16 min to 3.5–4.5 min of wall time and made 123 DOM tests really run (log :186). The required `gate` check came at 14:45 (log :187) [V].
- **A CI failure was root-caused, not retried.** On PR #19, `saveResume.test.ts` failed 2 of 3 CI runs. The builder found a real race in the test: 8.11's same-tick patches let the bots' Ready end the build before the Save, so Save and quit was refused `not_now`. The fix holds Ready in the test (8.11 B10, `8-11-…md:189`). The refusal behaviour itself was unchanged and pre-existing [V].
- **Two-tab smokes ran (Epic 6 A6).** Reports: `docs/perf/network-pass-smoke-2026-11-25.md` and `network-pass-smoke-8-1-2026-11-25.md`. 8.1's smoke found and fixed 3 bugs (log :95) [V].

## 4. What hurt

### H1. "Flaky" RunRoom.host.test.ts:206 was a real bug from 8.3

**Timeline:**
- **16:25:** first logged as "vi.waitFor 1 s flaky under load" and handed to the 8.7 builder as a CI follow-up (log :189).
- **16:25 to 21:20:** logged twice more as flaky, the second time with "fails on master too" (log :192, :202).
- **21:12:** master went red on 044522b (#18).
- **21:41:** fixed by PR #21 (9addaf0), a two-line fix in `syncState.ts` plus the client mirror (`eeb686b`, `d088292`) [V].

**The bug.** `syncBuildings` on the server and `mirrorBuildings` on the client copied a building's `owner` only when the entry was first created. A disown (E8-H3) therefore never reached a building that had already been sent. The test passed whenever no tick fell between `addBuildingAt` and the Remove. #20 (6861275) was green "by timing luck" (log :203) [V].

**What our review and test practice missed:**

1. **The story claimed a change the merge did not contain.**
   - Where: 8.2+8.3 T6 is ticked with "`syncState` now copies an owner change; the client mirror too" (`8-2-3-…md:61`). "Notes for the merge" repeats it (`:162`).
   - What merged: the PR #9 diff of `syncState.ts` adds only the `leftSeats` and `waiting` resets [V].
   - Who missed it: no review round checked that claim against the diff [V: review fixes `:257–283`; RR2 log :188].
2. **The named test exercised the claim only by timing.** Epic 6 A1 (named test per [x]) was satisfied in form. But the named test ran through the real room clock, so it tested the sync only when a tick happened to land in the right place. **No deterministic test** drove "sent, then changed, then synced" [V]. PR #21 added exactly that test (`syncState.test.ts`).
3. **The mutation hit the wrong layer.** Mutation M8 "buildings not disowned" (`:153`) was caught by an assert on the World. No mutation deleted the copy in the schema layer or the client mirror. Epic 6 A2 (wiring test per hookup) was written for scene hookups. The state → schema → mirror copy chain is the same kind of hookup and wasn't covered [V].
4. **The flaky label delayed the fix by about 5 hours.** Nobody tried a deterministic repro, such as forcing a tick between the add and the Remove. The label "flaky under load" was taken at face value three times [V: log :189, :192, :202].

**Pattern [V].** Of the load-sensitive failures of 25–26 November that someone investigated, **none was pure noise**:
- `cut.test`: a bot bug. Bots fired into their own barricade at Spitters, and that exposed a real Spitter deadlock (log :163).
- `saveResume`: a real race in the test (8.11 B10).
- `RunRoom.host:206`: a real product bug.
- `spots.test`: a 120 s single test, too big for a loaded shard (log :195).

### H2. Master went red after a merge with a green PR run (spots.test)

- **What happened:** the PR #8 (8.7) run was green, but master's run after the merge timed out: the all-stages stampede test in `spots.test` hit 120 s on a loaded shard (log :195).
- **Why it was missed:** "I checked the PR run, not master's." PR #17 split the test per stage.
- **The rule:** check master's run after every merge.
- **[I] Why the rule matters:** a PR's run is against its own merge ref at that moment, and the shard load differs on master.
