# Digest: Bluetooth and browser-native radio/local APIs (r1-1)

Question: can 2–4 phones (Android Chrome + iPhone Safari) play a 20 Hz server-authoritative browser game with no internet, using Bluetooth or other browser-native local APIs?

**Bottom line (from the evidence below):** Phone-to-phone Web Bluetooth is **not possible**. The spec and Chrome cover the central/client role only, with no peripheral, advertising or GATT-server role shipped or near, and iOS Safari has no Web Bluetooth at all. No browser API on these phones lets a web page open a raw local socket or Wi-Fi Direct link. The only web route left is ordinary networking over a shared LAN or hotspot, where Chrome's Local Network Access permission applies.

## Findings

### Web Bluetooth status (compat / spec)
- Chrome ships the Web Bluetooth GATT Communication API without a flag on Android 6.0+, ChromeOS, Mac and Windows. Linux is partial and behind a flag. `watchAdvertisements()` (Chrome 85) and the Scanning API are still behind flags on Android and Mac | https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md | Web Bluetooth CG | undated (living doc) | accessed 2026-11-23 | confidence medium (no dates on the page) | compat
- Firefox: "not supported, no near-term plans". Safari/iOS: not supported, no near-term plans. iOS browsers all use WKWebView. The only iOS options are the third-party apps WebBLE and Bluefy and a userland Safari extension polyfill (iOSWebBLE) | https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md | Web Bluetooth CG | undated | accessed 2026-11-23 | confidence medium | compat
- A Google Web Bluetooth engineer (Reilly Grant) wrote: "The WebKit project continues to be opposed to generic peripheral access APIs such as Web Bluetooth… WebKit is the only engine allowed on iOS"; it "has not been added to a major browser on iOS" (only purpose-built WebKit wrappers) | https://lists.w3.org/Archives/Public/public-web-bluetooth/2024Sep/0002.html | W3C public-web-bluetooth list | 2024-09-13 | accessed 2026-11-23 | confidence high (older than 12 months; I found no reversal) | policy
- MDN labels Web Bluetooth "Limited availability" (not Baseline) and experimental. Its GATT interface is `BluetoothRemoteGATTServer`, a server on a *remote* device. The page defines no local GATT server or peripheral interface | https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API | MDN | last modified 2025-05-27 | accessed 2026-11-23 | confidence high | spec
- A page cannot advertise or act as a peripheral. Spec issue #231 ("Advertisement / Beacon Broadcast Support") is still open. A maintainer said the first spec version covers "only the Central role". In Jan 2020 the maintainer (scheib) said "We're a long way off still from this". The issue tracks Chromium bugs for advertising-only and peripheral mode. Nothing is assigned and no PRs are linked. The last comment (Oct 2022) asks for exactly the P2P local-PWA sync use case | https://github.com/WebBluetoothCG/web-bluetooth/issues/231 | Web Bluetooth CG (GitHub) | 2016-04-26 opened, last activity 2022-10-16 | accessed 2026-11-23 | confidence high | spec
- **Conclusion: phone-to-phone over Web Bluetooth is impossible today.** Android Chrome can only be a central. No browser exposes a peripheral, advertising or GATT-server role, and iOS Safari has no Web Bluetooth at all. A workaround would need a native app on at least one phone, or Bluefy/WebBLE on iPhone, and even then each iPhone would be a central needing a peripheral to connect to | derived from the three sources above | — | — | accessed 2026-11-23 | confidence high | spec

### BLE performance (native only; performance)
- Minimum connection interval: iOS accepts 15 ms (except HID). Android accepts 7.5 ms. On iOS with a single connection, about 50% of a 15 ms interval is commonly allocated to connection events, which roughly halves the theoretical maximum. The theoretical app-level maximum is about 103.3 kB/s each direction. Neither OS exposes a connection-parameter API, so the peripheral must request parameters | https://punchthrough.com/ble-connection-interval-throughput/ | Punch Through | 2026-05-11 | accessed 2026-11-23 | confidence medium-high | performance
- Multiple simultaneous connections divide airtime and cause shortened or missed connection events. Punch Through gives no hard per-phone connection count and advises avoiding multiple connections and turning off advertising while connected | https://punchthrough.com/ble-connection-interval-throughput/ | Punch Through | 2026-05-11 | accessed 2026-11-23 | confidence medium | performance
- Measured by vendor: about 385 kbit/s iOS↔device and about 610 kbit/s Android↔device (2M PHY, 15 ms interval). This came from search-result summaries of Silicon Labs and other docs; I did not open the page | https://docs.silabs.com/gecko-os/1/bgx/1.x/throughput | Silicon Labs | undated | accessed 2026-11-23 | confidence low (search summary only) | performance
- A developer (iPhone 15 Pro, iOS 18.6.2, 30 ms interval fixed by the peer) reports noticeable latency and apparent batching of BLE notifications/writes on iOS versus "immediate" on Android. The thread has no replies and nothing from Apple | https://developer.apple.com/forums/thread/806188 | Apple Developer Forums | 2025-11 | accessed 2026-11-23 | confidence low (anecdote) | performance
- Rough arithmetic (my inference): a 20 Hz game sending 1–3 KB per tick per player needs 20–60 KB/s per link. For 3 clients that is 60–180 KB/s total from the host, which exceeds iOS's practical rate of roughly 50 kB/s per link and would be split across 3 connections. BLE looks marginal to infeasible at that payload size even natively. It only becomes plausible if packets shrink to about 200–500 B | derived | — | — | — | confidence medium (inference) | performance
- iOS natively supports acting as a BLE peripheral (CoreBluetooth peripheral role). Evidence: a developer thread titled "iOS Peripheral Throughput is low due to updateValue return false". Native phone-to-phone BLE is therefore possible in principle, but only from native apps | https://developer.apple.com/forums/thread/774300 | Apple Developer Forums | ~2025 | accessed 2026-11-23 | confidence medium (based on the title only) | compat

### Other browser APIs (one line each)
- **Web NFC:** Chrome for Android only. Desktop Chrome/Edge were behind a flag in v80–88 and never shipped. Not in iOS Safari through 27.2, Firefox or desktop Safari. Could at most carry a pairing token (e.g. a URL or IP) between Android phones | https://caniuse.com/webnfc | caniuse | data Oct 2026 | accessed 2026-11-23 | confidence high (caniuse only lists the current Chrome Android version, 157) | compat
- **Direct Sockets (raw TCP/UDP):** only in Isolated Web Apps, and IWAs exist only on ChromeOS. A June 2026 blink-dev PSA answers the platforms question with "Only ChromeOS". The Intent to Ship says Android is excluded and the API is not compiled into Android builds. Not usable on phones | https://groups.google.com/a/chromium.org/g/blink-dev/c/5cSZjgnJelk/m/ah5cM9gPAwAJ | Chromium blink-dev | 2026-06-10 | accessed 2026-11-23 | confidence high | compat
- **WebTransport:** supported in Chrome Android (current), iOS Safari 26.4+ and Firefox 114+. It is client-only (HTTP/3 to a server), so a phone page cannot host it. It needs a server process somewhere on the LAN, and in Chrome it is gated by the LNA permission | https://caniuse.com/webtransport | caniuse | data Oct 2026 | accessed 2026-11-23 | confidence high | compat
- **Local Network Access (Chrome 142+, Oct 28 2025):** a public `https://` page reaching a private or loopback address (e.g. 192.168.x.x) triggers a permission prompt ("Look for and connect to any device on your local network"). Chrome 145 split it into `local-network` and `loopback-network`. A service-worker request alone does not trigger the prompt. It is not a hard block: once granted, fetch with `targetAddressSpace:'local'` is exempt from mixed-content blocking | https://developer.chrome.com/blog/local-network-access | Chrome for Developers | 2025-06-09 (blog) plus vendor notes for the 142/145 dates | accessed 2026-11-23 | confidence high | policy
- LNA details: it gates fetch, WebSocket and WebTransport (`transport.ready`). `ws://` to a private IP literal, a `.local` host or `localhost` is exempt from mixed content (non-`.local` DNS names need `wss://`). LNA permissions are auto-denied in insecure top-level contexts. Checks apply only when a request goes from a less-private to a more-private address space, so a page served *from* the LAN host itself should not prompt (inferred from the rule, not stated outright). The page does not mention Android specifically | https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access.md.txt | Chrome for Developers | undated | accessed 2026-11-23 | confidence medium-high | policy
- **WebUSB:** Chrome for Android yes. iOS Safari no (through 27.2). Firefox no. Not relevant for phone-to-phone play | https://caniuse.com/webusb | caniuse | data Oct 2026 | accessed 2026-11-23 | confidence high | compat
- **Wi-Fi Direct from the web:** I found no shipped or proposed web API (see "Looked for but could not find") | — | — | — | — | confidence low (absence of evidence) | compat

## Leads worth chasing
- Bluefy and WebBLE on iOS: check whether either exposes any peripheral or advertising extension. Probably not, but it is unverified.
- Android Chrome's handling of LNA (mobile UI and prompt behaviour), and whether a page served over plain HTTP from a phone-hotspot host (same address space) avoids the prompt in practice.
- iOS Safari's own local-network behaviour for WebSocket/WebRTC to 192.168.x.x, including the iOS "Local Network" privacy prompt for Safari. This is outside this track but decisive for the hotspot/LAN route.
- WebRTC DataChannel over hotspot LAN with no STUN (host candidates only) and manual or QR signalling. Hand this to the WebRTC track. LNA interaction with WebRTC was not covered in the Chrome guide.
- EU DMA alternative browser engines on iOS (Blink-based Chrome in the EU): whether any shipped with Web Bluetooth by late 2026. I did not search this.
- WebKit standards-positions: I did not find a dedicated Web Bluetooth issue, so the 2017 WebKit bug "features not considered" (bugs.webkit.org) is worth checking for current wording.
- Silicon Labs and Punch Through measured numbers for multi-connection phone-as-central at 15 ms, to firm up the per-phone connection count.

## Looked for but could not find
- Any spec, explainer or Chromium intent for a Web Bluetooth peripheral, GATT-server or advertising role newer than 2022. Only open issue #231 and its tracking bugs exist.
- A dedicated WebKit standards-positions GitHub issue for Web Bluetooth with a dated "oppose" label. I relied on the 2024 W3C list statement instead.
- An authoritative per-phone BLE simultaneous-connection limit for Android or iOS.
- Any web API for Wi-Fi Direct or Wi-Fi Aware (NAN) in Chrome or Safari.
- An explicit statement that LNA applies identically on Android Chrome.
