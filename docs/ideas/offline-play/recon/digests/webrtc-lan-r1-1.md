# Digest: offline LAN WebRTC on phones (r1-1)

Decision served: can 2–4 phones (Android Chrome + iOS Safari) play a 20 Hz host-authoritative browser game over a phone hotspot or travel router with no internet, using WebRTC data channels and QR/manual signalling?

## Findings

### Q1: WebRTC on a LAN without STUN, and mDNS
- mDNS host candidates replace the private IP with a random `.local` name. The remote peer resolves it by multicast on the LAN, so peers on the same LAN can connect without STUN or TURN. Server-reflexive and relay candidates are unaffected, and they need servers anyway. | https://bloggeek.me/webrtcglossary/mdns | BlogGeek.me | 2026-04-07 (last updated) | accessed 2026-11-23 | confidence medium | class spec
- The IETF draft says mDNS names are only valid within the local network. Private IPs have the same limit, so same-LAN use is the intended case. | https://datatracker.ietf.org/doc/html/draft-ietf-mmusic-mdns-ice-candidates | IETF MMUSIC | 2021-12 (draft) | accessed 2026-11-23 | confidence high | class spec
- Chrome: when the page has camera or microphone (getUserMedia) permission, host candidates carry real IPs. Otherwise they are mDNS-masked. Rollout was Chrome 76 (Aug 2019). Measured connection-rate drop: about 2% when both sides use mDNS, 3–7% when the other endpoint lacks mDNS support. | https://groups.google.com/g/discuss-webrtc/c/6stQXi72BEU?pli=1 | Google discuss-webrtc (Qingsi Wang) | 2019-08-13/14 | accessed 2026-11-23 | confidence high (for 2019 Chrome desktop; current behaviour unverified) | class policy
- mDNS is the default in Chrome, Edge, Firefox and Safari. Chrome has the enterprise policy `WebRtcLocalIpsAllowedUrls` to exempt origins, which is not usable on friends' phones. Failure modes: multicast blocked means silent resolution failure (the candidate arrives but never pairs); network segmentation; ICE parsers that reject `.local`. | https://bloggeek.me/psa-mdns-and-local-ice-candidates-are-coming/ | BlogGeek.me | 2019-07-09 (updated, date not shown) | accessed 2026-11-23 | confidence medium | class compat
- Chrome on Android historically had no mDNS stack. In 2019 it sent plain IPs, and Chrome there uses the system resolver, which did not support mDNS at the time. A later report, cited secondhand from Android docs, says the Android resolver supports `.local` since Nov 2021, except over VPN or mobile data. Current Chrome Android generation and resolution of `.local` was NOT verified this run. | https://groups.google.com/g/discuss-webrtc/c/6stQXi72BEU ; search summary of Mozilla bug threads (e.g. https://bugzilla.mozilla.org/show_bug.cgi?id=1581947) | discuss-webrtc / Mozilla Bugzilla | 2019 / ~2021+ | accessed 2026-11-23 | confidence low | class compat
- Firefox enabled mDNS host obfuscation on Android in Firefox 149 (bug resolved fixed). The bug says "Android seems to be capable of supporting our current implementation of mDNS… may not be the case on all devices especially older ones." | https://bugzilla.mozilla.org/show_bug.cgi?id=2011711 | Mozilla Bugzilla | ~2026 (relative date "10 months ago") | accessed 2026-11-23 | confidence medium | class compat
- An anecdotal report from an IPv6-only device: only mDNS candidates appeared until microphone permission was granted, then real IPv6 host candidates appeared. This supports a workaround: request getUserMedia permission (audio, then stop the track) to unmask host IPs. | search summary of discuss-webrtc threads (https://groups.google.com/g/discuss-webrtc/c/PFj1J4cwnwY) | discuss-webrtc | unknown | accessed 2026-11-23 | confidence low | class compat
- libwebrtc filters link-local and loopback addresses from host candidates. It also has a `disable_link_local_networks` option, added after an iPhone link-local interface caused failures. This matters for the iOS 18 hotspot finding below. | https://chromium.googlesource.com/chromium/src/+/ba6887034587e01ee3c166c0d9aa902537dfd1ed ; https://webrtc.googlesource.com/src/+/2870b0a57e68be61331ba9b8b38e762d41a242ba | Chromium / WebRTC source | unknown | accessed 2026-11-23 | confidence low (from search summary; commits not read) | class compat

### Q2: Phone hotspots with no mobile data
- Apple describes Personal Hotspot as sharing the iPhone's cellular connection. Forum consensus is that it only works with cellular data on. No Apple statement was found on whether it is greyed out with no signal. | https://support.apple.com/111785 ; https://discussions.apple.com/thread/6037269 | Apple Support / Apple Community | various | accessed 2026-11-23 | confidence medium (that it is unreliable or unavailable without data) | class policy
- **iOS 18.0+ Personal Hotspot: every client shows IPv4 192.0.0.2 with no subnet mask. IPv4 client-to-client traffic (even ping) fails, and broadcast or multicast to clients stopped. Apple's Feedback team: "you can't use IPv4 to communicate between client devices, you have to use IPv6. IPv6 link-local is perfect for this." This worked on iOS 16/17 hotspots. Apple DTS (Quinn): Personal Hotspot is "a user-level feature, not an API… focus… is STA-to-Internet," and DTS is "not aware of any specific change to isolate your app running on the iPhone from the various STAs."** | https://developer.apple.com/forums/thread/773086 | Apple Developer Forums (DTS + Feedback Assistant reply) | 2025-01/02 | accessed 2026-11-23 | confidence high (for the client-to-client IPv4 break) / low (for hotspot-host-to-client still working) | class compat
- On older iOS (around iOS 14), clients on a 172.20.10.x hotspot could reach each other, and the iPhone at 172.20.10.1 could reach a client at 172.20.10.2. | https://forum.openwrt.org/t/ios14-tethering-issues/74949/11 | OpenWrt forum | ~2020 | accessed 2026-11-23 | confidence low (superseded by iOS 18) | class compat
- A game developer reports that no broadcasts or multicasts are released onto the network when an iPhone hosts the hotspot. This is relevant to mDNS candidate resolution, which needs multicast. | https://forums.solar2d.com/t/udp-communication-fail-using-iphones-personal-hotspot/347951 | Solar2D forum | unknown (older) | accessed 2026-11-23 | confidence low | class compat
- Android: a hotspot without a SIM works on some devices and is blocked on others ("Insert SIM card" error, carrier-locked phones). A SIM-less hotspot gives a local-only network "in the field between a number of devices." | https://code.briarproject.org/briar/briar/issues/1646 ; https://forums.androidcentral.com/threads/using-mobile-hotsot-with-just-wifi-enabled-and-no-valid-sim.774528 | Briar project / Android Central forum | unknown | accessed 2026-11-23 | confidence low-medium | class compat
- Android `WifiManager.startLocalOnlyHotspot` is an app-level API ("Request a local only hotspot that an application can use to communicate between co-located devices"). A web page cannot call it. A native app (or a TWA wrapper with native code) would be needed. | https://developer.android.com/reference/android/net/wifi/WifiManager | Android Developers | current | accessed 2026-11-23 | confidence high (exists, app-only); details on internet and permissions not read | class policy
- Android "no internet" Wi-Fi: Samsung (Intelligent Wi-Fi, "Switch to mobile data") and Pixel (Wi-Fi preferences) can switch away from or disconnect a no-internet Wi-Fi. Users report adding a "network exception" to stay connected. With no mobile data at all there is nothing to switch to, but the setting still matters. | https://forums.androidcentral.com/threads/using-internet-connected-to-local-wifi.1043546 ; https://us.community.samsung.com/t5/Galaxy-S22/Using-cellular-data-while-connected-to-a-LAN-that-doesn-t-have/m-p/2680835 | Android Central / Samsung Community | unknown | accessed 2026-11-23 | confidence low | class compat

### Q3: Manual and QR signalling
- Serverless WebRTC with manual or QR exchange exists: serverless-webrtc-qrcode (fta2012, dcerisano forks), tomashubelbauer/webrtc-qr-signaling-channel, and a Google patent (US10069872) on SDP in QR codes. | https://github.com/fta2012/serverless-webrtc-qrcode ; https://github.com/tomashubelbauer/webrtc-qr-signaling-channel ; https://patents.google.com/patent/US10069872 | GitHub / Google Patents | various | accessed 2026-11-23 | confidence medium (exists; current function not tested) | class spec
- Measured SDP for an audio call: 2,847 chars raw, 3,796 base64. That exceeds the roughly 2.9 KB binary QR limit, so the author split it into 1,000-char chunks (4 QR scans). Verdict: "technically possible, but the UX is rough." A data-channel-only SDP should be smaller, but it was not measured here. | https://lilting.ch/en/articles/webrtc-qr-signaling | lilting.ch | 2026-01-11 | accessed 2026-11-23 | confidence medium | class performance
- QWBP (QR-WebRTC Bootstrap Protocol) is an independent informational draft by M. Garcia Monterde. It reduces signalling to a binary packet of about 41–110 bytes: SHA-256 DTLS fingerprint plus candidates (IPv4, IPv6 or mDNS UUID as 16 bytes) plus port. ICE ufrag and pwd are derived from the fingerprint with HKDF. It takes one QR each way (2 scans per pair), requires complete ICE gathering (+1–2 s), and the answerer rolls back its own offer. It notes Chrome and Safari hide IPs behind mDNS. | https://magarcia.github.io/qwbp/spec.html | magarcia.github.io (self-published) | 2026-01-19 | accessed 2026-11-23 | confidence medium (spec read; no independent interop evidence) | class spec
- W3C webrtc-pc issue #2945 discusses manual exchange with candidates gathered to completion before encoding. | https://github.com/w3c/webrtc-pc/issues/2945 | W3C WebRTC WG GitHub | unknown | accessed 2026-11-23 | confidence low (not read) | class spec
- BarcodeDetector: Chrome for Android is supported (listed v157). iOS Safari 17.0–27.2 has it **disabled by default**, and Firefox does not support it. Use a JS fallback (e.g. jsQR or zxing-wasm) on iOS. | https://caniuse.com/mdn-api_barcodedetector | caniuse | current | accessed 2026-11-23 | confidence high | class compat

### Q4: Data channel performance
- `maxRetransmits` is supported in Safari 11 through 26.x per caniuse. MDN lists it as Baseline (widely available) since Jan 2020. `ordered: false` is supported in Safari iOS 11+. | https://caniuse.com/mdn-api_rtcdatachannel_maxretransmits ; https://caniuse.com/mdn-api_rtcdatachannel_ordered ; https://developer.mozilla.org/docs/Web/API/RTCDataChannel/maxRetransmits | caniuse / MDN | current | accessed 2026-11-23 | confidence medium-high | class compat

### Q5: Libraries
- Trystero's signalling strategies are Nostr, MQTT, BitTorrent, Supabase, Firebase, a self-hosted ws-relay, and custom strategies. Its defaults use public internet relays, and no offline or manual mode is documented. A custom strategy is the only possible hook. | https://github.com/dmotz/trystero | GitHub (dmotz) | current | accessed 2026-11-23 | confidence medium | class spec
- PeerJS uses a PeerServer, either its free cloud server or a self-hosted one. No manual or offline signalling is documented on its homepage. | https://peerjs.com/ | PeerJS | current | accessed 2026-11-23 | confidence medium | class spec

## Leads worth chasing
- **Highest risk:** iOS 18+ hotspot blocks IPv4 client-to-client traffic. Do Safari and Chrome emit usable IPv6 host candidates on that network? libwebrtc filters link-local, so possibly not. Does the hotspot iPhone itself still reach clients over IPv4? That would allow a star topology with the hotspot phone as game host. A real-device test is needed: iPhone hotspot (iOS 18/26) with an Android and an iPhone client, using a simple WebRTC page with candidates logged.
- Is multicast mDNS resolution of `.local` candidates possible on an iPhone hotspot, given broadcast and multicast are reportedly not forwarded? If not, the getUserMedia-permission trick to unmask raw IPs may be the main workaround. Need to verify that Safari iOS unmasks host IPs after getUserMedia, and that Chrome Android does too.
- Current Chrome Android mDNS behaviour (crbug search "mdns android"). Does it now emit `.local` candidates, and can it resolve iOS-generated `.local` names?
- A travel router (no client isolation, AP mode) avoids the iPhone hotspot problems entirely. Verify that Android and iOS stay joined to a no-internet SSID, and how iOS handles the captive-portal assistant.
- Measure data-channel-only SDP size, and whether QWBP-style SDP reconstruction (munging a remote SDP from fingerprint + candidate) works in Safari.
- Android Wi-Fi-only "Keep Wi-Fi connected" prompt on no-internet networks: find the AOSP NetworkMonitor docs for the "no internet access, stay connected?" dialog.
- Chromium Local Network Access permission prompts (2025–26): could they affect WebRTC to private IPs from an https page? Unverified.
